# Start Use Case

Portable launcher: it finds the task file of the current use case and hands
control to it. It does not contain any business logic.

The canonical entry point is the `TASK.md` of the use case directory — the
directory the harness was started from, e.g.
`paul/finance/contract-management/obligations/`.

## 1. When this skill applies

### Implicit launch — first turn only

Generic start phrases such as:

```text
go · vas-y · commence · commençons · allons-y · démarre · start · let's go
```

mean "start the task defined by the current use case" **only when they are the
first substantive operational instruction of the current conversation**.

```text
Implicit launch behavior is valid only for the first substantive operational
instruction of the current conversation.

Do not reinterpret generic continuation phrases later in an ongoing
conversation as a request to reload or restart the workspace task.
```

Later in a conversation, `go`, `vas-y`, `continue`, `ok go` or equivalent
phrases continue the current step in the current context. They never reload
the task file and never restart the use case from scratch.

Greetings or small talk before the start phrase do not count as operational
instructions.

### Explicit launch — any time

Explicit requests are valid at any point of the conversation:

```text
exécute TASK.md
lance le use case obligations
lance contract review
reprends le use case obligations
relance la tâche monthly report
```

## 2. Resolving the task file

### Implicit launch

Look **only in the current directory** — the use case directory the agent was
started from. Do not walk up the business hierarchy, and do not use the
enclosing Git root (`paul`) as the entry point. Take the first match in this
order:

```text
1. TASK.md
2. USE_CASE.md
3. USE-CASE.md
4. USE_CASE_*.md / USE-CASE-*.md
5. TASK_*.md
6. MISSION*.md
7. RUN_*.md
8. the same names with a .txt extension
```

`TASK.md` is the canonical entry point generated by `create-use-case`.

Never search implicitly inside:

```text
workspace-*/  .agents/  .git/  .pi/  .hermes/  node_modules/  evaluator/
```

These contain business data (the nested `workspace-<slug>` repository), skills,
harness configuration or evaluation material. A task file found there is not
the entry point of the use case and must not be launched implicitly — even
when `workspace-<slug>/TASK.md` exists, the implicit launch from the use case
directory takes the use case's own `TASK.md`.

If one level of the list contains several candidates (for example two
`USE_CASE_*.md` files), ask the user which one to run. If exactly one
reasonable candidate exists, use it.

If nothing is found, say so in one line and ask what to run. Do not invent a
task.

### Named launch ("lance le use case obligations")

1. Normalise the requested name and the candidate names: lower case, remove
   accents when possible, treat spaces, `_` and `-` as equivalent.
2. Match against, in order:
   - the task files listed above in the current directory (e.g.
     `USE_CASE_contract-review.md` matches "contract review");
   - the name of the current use case directory (e.g. `obligations`);
   - the use case directories below the current directory that contain a task
     file (a business folder holding several use cases). Skip `workspace-*`,
     `.agents/` and `evaluator/` while searching.
3. One plausible match → load it. Several → ask which one. None → say so.

An explicit request may name a file anywhere the user points to; the implicit
exclusions above only apply to implicit launches.

## 3. Running the task

1. Read the resolved task file entirely.
2. If it delegates to another file (for example an `AGENTS.md` holding the
   durable rules of the main agent, or a specification), read that file too
   and follow it.
3. Execute the task as written, from the directory that contains the resolved
   task file.
4. Mention in one line which file is being executed.

## 4. Resume

This skill may resolve *which* task to resume ("reprends le use case X"), but it
does not implement resume logic.

If the use case has persistent state in its workspace
(`workspace-<slug>/state/`, `workspace-<slug>/data/*.duckdb`, a `NEXT_ACTION`
field, a progress table…), the task file is responsible for using it. Follow its resume instructions; do not restart
from scratch unless the task file or the user asks for it.

## 5. Out of scope

- No business logic.
- No harness-specific extension or command is required: the skill only reads
  files with the standard file tools of the current harness.
- It does not guarantee mechanically that a phrase is the first turn: the
  agent applies the rule in §1 from the conversation it can see.
